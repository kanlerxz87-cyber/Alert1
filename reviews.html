Live game state

Every game on the slate, captured from the official feed the moment it changes — score, inning, outs, count, batter, pitcher, pitch count, runners — time-stamped to the second with its Gameday timecode, plus the before → after of the latest change and MLB's own wording.

✏️ Official scoring ledger

A separate, persistent log — not part of the alert path — of official-scorer pending rulings on at-bats that have not been scored yet, and of every scoring change when the official scorer changes the outcome of an at-bat or play. Each record keeps the before and after official state, both official descriptions, second-precision timestamps, and is saved to this browser (and to the local server when one is running) so a refresh loses nothing. Export it as JSON or CSV at any time.

Unofficial fan project. Live data via the public MLB StatsAPI (statsapi.mlb.com) — manager challenges, crew chief/umpire reviews and boundary calls come from the live game feed's reviewDetails, ABS pitch challenges from absChallenges / pitch-level review events, and official-scorer pending rulings (hit vs. error vs. fielder's choice undecided) come from the API's own event-type registry — os_ruling_pending_primary / os_ruling_pending_prior, description "Official Scorer Ruling Pending" (GET /api/v1/eventTypes). A pending ruling decides how the play is charged and never removes a run from the score. Challenges-remaining counters are the official per-team values read directly from the StatsAPI (review.away/home.used/remaining for manager challenges; gameData.absChallenges.away/home.usedSuccessful/usedFailed/remaining for ABS) — never derived by counting feed events, and never zero-filled when a counter is absent (e.g. pre-ABS seasons). A used-counter that moves backwards between polls is flagged as an irregularity on the affected rows instead of being corrected or hidden. The score tracker separates the observed call-on-field score, conditional possibilities, and an attributable official score after resolution when exposed. Possibilities use only runs tied to the reviewed event and are not predictions of the ruling or runner placement. A review is flagged Runs at Risk only when the official payload credits one or more scoring movements to the very event under review, so an overturn could take those runs back off the scoreboard. Unrelated runs from earlier in the same plate appearance (a steal of home, a wild pitch) are excluded, and whether replay actually removes a run is never predicted. Official scoring changes (a hit reclassified as an error or vice versa, a single changed to a double or back, a base hit changed to a fielder's choice + error, an out changed to a hit, and so on) are tracked in the ✏️ Scoring Changes tab and in the All feed by snapshotting every completed play's official classification (result.eventType / result.isOut / count.outs / error movements in runners[]) on every poll and diffing it against the previous polls — the StatsAPI payload carries no scoring-change marker, so the initial call and the final ruling are known only from consecutive observations. Each row shows the observed initial call and the final ruling, the official score after the play, and an attribution note. Changes that coincide with a replay review stay on that review's row; everything else is attributed as an official scoring change (per MLB's own log, changes are made by the Official Scorer, the Elias Sports Bureau, or after a player/club review — mlb.com/official-information/scoring-changes). A change can only be tracked when its initial call was observed before the change landed; finals are re-scanned for 30 minutes after they end (at most every 30 seconds) to catch rulings published after the game. Payload edits without a reclassification (description / RBI / score only) and plays that vanish from the payload are flagged as irregularities for review, never corrected or hidden. Every tracked entry is also logged to this browser (one log per date, newest seven dates kept, 500 most-recent rows) so a refresh or a later visit restores the feed rows, the scoring baselines and the flagged irregularities before the first scan runs; the log holds only observed payload data, and anything malformed in it is dropped with a console warning rather than guessed. How fast this page can be: live games are updated from Gameday's own push channel (wss://ws.statsapi.mlb.com/api/v1/game/push/subscribe/gameday/{gamePk}) and, as the backstop, from the official delta endpoint GET /api/v1.1/game/{{gamePk}}/feed/live/diffPatch?startTimecode=… — RFC 6902 changes against a copy of the feed already held, polled every 250 ms (150 ms while a review is open) and seeded from the full feed, which is also the recovery path when a patch cannot be applied. Whether a play reaches the API in one second or ten is MLB's publication cadence, not this page's; what this page removes is its own share of the delay. The Live game state section shows, per game, the captured state with its second-precision timestamp, the official Gameday timecode and the transport that delivered it. The Official scoring ledger is a separate store (mlbp.scoringledger.v1.* in this browser, or data/scoring-ledger-<date>.json when node server.mjs serves the site) so a refresh cannot lose a pending ruling or a scoring change, and so nothing in it can interfere with the alert feed. The alert sound is one ~3 s raindrop, off by default, with a Test button that says whether it actually played.
